# 战略与知识工程设计

## 决策摘要

Legal AI Lab 的长期目标是建设覆盖多个法律领域的 AI 法律服务基础设施，并逐步发展知识图谱、风险分析与结果预测能力。首个“欠薪”场景不是产品边界，而是验证通用知识生产、检索、推理、引用和评测能力的样板。

当前阶段以官方公开资料研究为主，不把用户访谈作为建立知识库的前置条件。访谈、真实用户反馈与专业复核在原型和试点阶段用于补充验证。

## 产品演进

```text
通用法律入口
  -> 领域与问题识别
  -> 专业领域模块
  -> 事实采集、证据整理、规则与案例检索
  -> 风险分析、行动建议与来源引用
  -> 必要时转人工律师
```

### 阶段 A：欠薪知识引擎

建设可复用的来源管理、规则卡、证据卡、程序卡、案例卡、小型知识图谱、混合检索、引用校验和自动评测能力。

### 阶段 B：劳动争议模块

按相邻主题扩展：未签书面劳动合同、违法解除、加班工资、经济补偿、社会保险、工伤、劳务派遣和新就业形态。

### 阶段 C：多领域法律模块

在每个新领域分别完成事实模型、证据模型、程序模型、权威来源和评测集后，再接入合同、消费者权益、婚姻家事、交通事故或企业合规等模块。

### 阶段 D：结果分析

先提供证据充分度、程序风险、请求完整度、相似案例和不确定因素；在拥有可合法使用、去标识化、时间切分正确且经校准的数据集后，再研究单项请求支持概率、金额区间和置信区间。

## 胜率功能边界

“胜率”不是单一事实。必须分别定义：请求是否获得支持、支持比例或金额、调解结果、仲裁或诉讼结果、以及执行回款结果。

在以下条件满足前，产品不得对用户输出确定的胜率百分比：

- 数据覆盖仲裁、调解、诉讼和执行等不同结果，且来源合法。
- 输入特征只包含案件开始时可获得的信息，避免使用判决书中的事后信息造成数据泄漏。
- 模型按地区、时间、争议类型、证据状态和请求类型进行独立验证。
- 输出包含适用范围、置信区间、关键不确定因素和可解释依据。
- 经法律专业人员与合规审查后，确认表达方式不会被误解为结果保证。

在此之前，使用“风险分层 + 证据评分 + 相似案例 + 待核实因素”替代胜率。

## 小型法律知识图谱

第一版只定义稳定、可复用的核心实体：

```text
劳动者、用人单位、劳动关系、事件、请求、证据、法律规则、程序、期限、地区、案例、结果
```

核心关系包括：

```text
劳动者 --工作于--> 用人单位
事件 --发生于--> 日期
请求 --基于--> 事实
请求 --需要--> 证据
请求 --适用--> 法律规则
法律规则 --受限于--> 地区和生效时间
案例 --解释--> 法律规则
程序 --前置于--> 后续程序
证据 --证明--> 事实
```

知识图谱用于表达关系和约束；RAG 用于检索原文；规则引擎处理明确的流程和计算逻辑；LLM 负责理解、追问、结构化与解释。四者不能互相替代。

## 欠薪知识包

### 1. 来源登记表

每个来源必须记录：

```yaml
source_id:
title:
issuing_authority:
source_type:
official_url:
publication_date:
effective_date:
status:
jurisdiction:
retrieved_at:
content_hash:
license_or_terms_note:
supersedes:
superseded_by:
```

`content_hash` 用于监测官网内容变化。任何知识卡都必须可回溯至原始来源。

### 2. 法律规则卡

法规按可检索、可判断的规则拆分，而不是把整部法律直接交给模型。

```yaml
rule_id:
title:
domain: labor
topic: wage_arrears
jurisdiction:
effective_from:
effective_to:
status:
conditions: []
legal_effect:
exceptions: []
facts_required: []
evidence_related: []
procedure_related: []
source:
  document:
  article:
  official_url:
review_status: draft
```

### 3. 场景、证据、程序和案例卡

- 场景卡：定义必问事实、可能责任主体、证据清单、规则、流程、风险和转人工条件。
- 证据卡：说明某类证据可以支持什么、不能单独证明什么、如何保存以及隐私风险。
- 程序卡：记录进入条件、主管机关、材料、步骤、可能结果、期限、地区差异与风险。
- 案例卡：记录事实、争点、请求、证据、适用规则、裁判理由、结果、局限与权威来源；案例不能被写成普遍规则。

## 来源白名单与优先级

### P0：直接法律依据

- 国家法律法规数据库：法律、行政法规、部门规章及有效状态。
- 全国人大、中国政府网、人力资源和社会保障部。
- 最高人民法院公布的司法解释。

### P1：权威解释与案例

- 最高人民法院典型案例与人民法院案例库。
- 人力资源和社会保障部、全国总工会及地方人社、法院的官方材料。

### P2：普通公开裁判文书

用于发现争议类型、证据模式和地区差异，不自动提升为一般规则。

### P3：二手内容

律师文章、媒体和问答只能用于发现用户语言与研究线索，不能作为最终法律依据。

首批来源应覆盖劳动法、劳动合同法、劳动争议调解仲裁法、劳动保障监察相关规定、保障农民工工资支付条例、现行劳动争议司法解释及目标地区工资支付规定。采集前须再次核验每份文件的现行有效状态。

## 自动化知识生产流程

```text
官方来源白名单
  -> 发现页面与下载原文
  -> 保存快照、元数据和内容哈希
  -> 按条款或案例结构切分
  -> LLM 提取候选结构化数据
  -> 来源、时效、条款和冲突校验
  -> 草稿知识库
  -> 抽样专业复核
  -> 发布到检索库与知识图谱
```

原始文本、规范化文本和结构化知识必须分层保存：

```text
raw/         原始网页或文件快照
normalized/  清洗后的规范文本
knowledge/   规则卡、案例卡、证据卡和程序卡
```

不得让模型修改原始文本；不得绕过网站访问限制；必须遵守来源网站的使用规则和版权要求。

## 质量与评测

没有访谈时，优先建立三层测试集：

1. 规则合成案例：组合合同、在职状态、支付方式、证据、主体和程序等变量。
2. 官方案例改写：保留权威案例的事实结构，去标识化并构造信息不足、矛盾陈述和缺失证据版本。
3. 对抗案例：测试编造引用、过度承诺、资料失效、程序遗漏、隐私泄露和提示注入。

发布门槛：每个用户可见结论均应区分“用户确认事实”“待核实信息”“系统解释”和“外部来源”；每条法律信息都应显示来源、查询日期和适用限制。
