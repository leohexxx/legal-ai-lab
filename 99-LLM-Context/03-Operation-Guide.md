## 1. 如何"理解"专家提示词

### 1.1 提示词的结构语言

本项目每个提示词（`.md` 文件）使用了一套**标准结构**，读懂这套结构就能快速理解任何专家：

```
文件头：标题 + 一句话定位 → 告诉我"这是谁"
核心定位/使命         → 告诉我"为什么存在"
核心能力列表          → 告诉我"能做什么"（按技能/能力分组）
工作流程             → 告诉我"怎么做"
输出模板             → 告诉我"交付什么"
边界与原则           → 告诉我"不能做什么"
触发场景             → 告诉我"什么时候叫他"
协作关系             → 告诉我"和谁配合"
```

### 1.2 理解提示词的 3 个关键问题

读每个提示词时，先问自己：

| 问题 | 寻找位置 |
|------|----------|
| **这个专家在什么场景下使用？** | 触发场景 / 典型场景 段落 |
| **这个专家交付什么产物？** | 输出模板 / 交付物 段落 |
| **这个专家的边界在哪里？** | 边界与原则 / 禁止 段落 |

### 1.3 注意：提示词是"角色卡"不是"指令"

这些提示词定义的是**角色和能力范围**，不是一次性指令。使用方式：
- 当任务匹配某个专家的能力范围时，加载对应的提示词文件
- 提示词定义了这个专家**应如何思考和工作**，具体的任务描述需要在加载后补充
- 不同专家的提示词可以串联使用（一个的输出作为下一个的输入）

## 2. 如何"操作"专家提示词

### 2.1 单专家使用（最常见的场景）

```
判断任务类型 → 找到匹配的专家 → 加载其提示词 → 给出具体任务 → 获取输出
```

**示例**：
1. 用户说"帮我写一个欠薪功能的 PRD"
2. 匹配到专家 → **产品通**（`产品管理专家提示词.md`）
3. 加载提示词 + 补充当前上下文（用户需求原文）
4. 产品通输出 PRD 文档

### 2.2 多专家串联（标准 SOP 工作流）

当任务需要跨角色协作时（如"开发一个新页面"），使用齐活林 SOP 流程：

```
用户需求
  → 主理人(齐活林)判断走哪种工作流
    → 快速模式: 直接调工程师
    → 标准SOP: 产品通(PRD) → 架构师(设计) → 工程师(代码) → QA(测试)
```

**关键规则**：每个阶段的输出文件必须存盘，作为下一阶段的输入。
实践方法：
1. 产品通输出 PRD → 保存为 Markdown 到 `01-Product/`
2. 架构师输出设计文档 → 保存到 `03-AI-Technology/` 或相关目录
3. 工程师输出代码 → 保存到 `frontend/` 或 `app/`
4. QA 输出测试结果 → 保存到 `tests/`

### 2.3 并发使用（独立任务）

当多个任务相互独立时，可以同时加载多个专家并行处理：

```
任务A: 法检Pro → 检索劳动法条文
任务B: UI设计师 → 设计组件样式
任务C: 工程师 → 修复已知Bug
```

## 3. 项目操作规范

### 3.1 文件操作规则

| 操作 | 规则 |
|------|------|
| **读取** | 先读 `99-LLM-Context/README.md` 确定导航，再按需读具体文件 |
| **写入** | 按编号体系放入对应文件夹（`00-`到`08-`），不要随意创建新顶层目录 |
| **修改** | 保存旧版本（git），不要直接覆盖不明内容 |
| **删除** | ⚠️ 默认不删除，除非用户明确确认。删除前必须解释原因 |

### 3.2 代码操作规则

| 场景 | 规则 |
|------|------|
| 前端开发 | Next.js 16 → `frontend/` 目录 |
| 后端开发 | FastAPI → `app/` 目录 |
| 安装依赖 | `npm install`（前端） / `pip install`（后端，用 venv） |
| 启动 dev | `npm run dev`（前端） / `uvicorn app.main:app`（后端） |
| 测试 | `pytest tests/`（后端） / 手动验证（前端） |
| 提交 | `git` → 推送到 `github.com/leohexxx/legal-ai-lab` |

### 3.3 专家加载优先级

当任务需求模糊时，按以下优先级判断调用哪个专家：

```
1. 用户明确指定 → 直接加载指定专家
2. 开发类任务 → 先走 齐活林 SOP（判断走哪种模式）
3. 法律类任务 → 法检Pro（检索） 或 技信衡（审核）
4. 设计类任务 → UI设计师
5. 产品类任务 → 产品通
6. 未明确 → 先读 README + 02-Shared-Foundation.md 建立语境
```

## 4. 常见操作流程

### 4.1 开发一个新页面

```
1. 确认需求 → 走 SOP（快速模式或标准SOP）
2. 如果是S2-S5范围内的页面 → 参考 Frontend_Delivery_Slices_S1_to_S5.md
3. 创建 `frontend/src/app/<page-name>/page.tsx`
4. 如果需要改造已有页面 → 先读原文件再改
5. 验证: `npm run dev` → 浏览器打开确认 200 OK
```

### 4.2 增加法律知识

```
1. 确认来源在 P0/P1 白名单内
2. 下载原文 → `data/raw/`
3. 清洗文本 → `data/normalized/`
4. 生成知识卡 → `data/knowledge/<domain>/`
5. 更新 INDEX.md
6. 运行 `scripts/hybrid_retrieval_demo.py` 验证检索
```

### 4.3 故障排查

```
前端异常:
  1. 检查 `next.config.ts` 配置
  2. 检查 NODE_OPTIONS 环境变量是否干扰
  3. 删 node_modules + npm install 重装
  4. 清 .next 缓存重建

后端异常:
  1. 检查 Docker 容器状态
  2. 检查数据库连接和迁移
  3. 检查环境变量

检索失败:
  1. 确认知识卡数据存在
  2. 确认中文分词正常（bi-gram + 术语扩展）
  3. 检查 query expansion 字典
```
