## 3. 向量化方案

### 3.1 Embedding 模型选择

**推荐方案：BAAI/bge-large-zh-v1.5**

| 维度 | 值 |
|------|-----|
| 模型 | BAAI/bge-large-zh-v1.5 |
| 维度 | 1024 → **通过降维映射为768维**（与现有 schema 兼容） |
| 备选1 | **moka-ai/m3e-base**（768维，中文通用，轻量） |
| 备选2 | shibing624/text2vec-base-chinese（768维，中文法律场景可用） |
| 备选3 | 智源研究院 BAAI/bge-base-zh-v1.5（768维） |

**推荐理由**：bge-large-zh-v1.5 在中文法律检索场景的 MTEB 中文榜排名靠前，支持指令调优。m3e-base 可作为轻量备选，768维与 schema 直接兼容。

**首选用 m3e-base（768维）**：
- 与 `embedding VECTOR(768)` 完全匹配，不用改 schema
- 推理速度比 bge-large 快约 3 倍
- 开源 MIT 协议无商用限制

### 3.2 分块策略

法律文本分块需要考虑条款边界的完整性。分块粒度直接影响检索召回质量。

```
┌──────────────────────────────────────────┐
│  层级1: 整部法规                          │
│  嵌入粒度 -> 用于"领域识别"                │
├──────────────────────────────────────────┤
│  层级2: 单一条款（规则卡粒度）              │
│  嵌入粒度 -> 核心检索单元，每张规则卡一条    │
│  ← 这是主要检索粒度                       │
├──────────────────────────────────────────┤
│  层级3: 相关条款聚合（主题包）              │
│  同主题多条规则聚合嵌入 -> 用于"主题匹配"    │
└──────────────────────────────────────────┘
```

**具体规则**：

| 规则 | 说明 |
|------|------|
| 以**条款**为最小不可分割单位 | 一条法律条款是一个完整语义单元，不允许跨条款切分 |
| 同一规则卡 = 一个嵌入向量 | 每条规则卡独立生成 embedding，维度 768 |
| 规则卡元数据同步索引 | jurisdiction、effective_from/to、domain、topic |
| 每部法规额外生成"摘要嵌入" | 用于快速过滤领域（labor/civil/contract） |

### 3.3 存储方案

直接在 PostgreSQL 中完成，**不引入独立向量数据库**：

```
知识库
  ├── knowledge.rules       ← 规则卡+embedding
  │     ├── embedding VECTOR(768) ← 语义检索
  │     ├── title TEXT           ← 全文检索
  │     └── legal_effect TEXT    ← 全文检索
  │
  ├── knowledge.evidence    ← 证据卡
  ├── knowledge.procedures  ← 程序卡
  └── knowledge.cases       ← 案例卡+embedding（后续扩展）
```

## 4. 检索算法细节

### 4.1 全文检索（FTS）得分

```sql
-- 对规则卡的标题和法律效果字段做全文检索
SELECT 
    rule_id,
    ts_rank(to_tsvector('simple', title || ' ' || legal_effect), query) AS fts_score
FROM knowledge.rules, plainto_tsquery('simple', '拖欠工资') AS query
WHERE to_tsvector('simple', title || ' ' || legal_effect) @@ query
ORDER BY fts_score DESC;
```

**权重策略**：
- 标题命中：加权 × 1.5
- 法律效果命中：加权 × 1.0
- conditions 命中：加权 × 0.8

### 4.2 语义检索得分

```sql
-- 使用余弦相似度
SELECT 
    rule_id,
    1 - (embedding <=> query_embedding) AS semantic_score
FROM knowledge.rules
ORDER BY embedding <=> query_embedding
LIMIT 20;
```

### 4.3 融合公式

```
final_score = 0.4 × normalized(fts_score) + 0.6 × semantic_score
```

**为什么语义权重高于全文**：
- 用户输入是自然语言（"老板不给钱"），与法条原文（"工资应当以货币形式按月支付"）用词差异大
- 语义模型能跨术语匹配
- 全文检索作为安全网，确保精确术语也能命中

### 4.4 元数据过滤

融合后按以下过滤器剔除不合格结果：

| 过滤器 | 逻辑 | 优先级 |
|--------|------|--------|
| 效力状态 | status != 'active' 的直接剔除 | 强制 |
| 生效日期 | effective_from > now 或 effective_to < now 的剔除 | 强制 |
| 管辖地区 | 匹配用户所在地区（全国默认匹配所有） | 非强制 |
| domain/topic | 与场景识别结果匹配 | 场景依赖 |

## 5. 检索原型实现路径

### Phase 1：文件级检索（立即可做）

```text
用 Python 脚本模拟：
  1. 读取 YAML 规则卡 → 生成 embedding（调用外部 API）
  2. 接收查询 → 分别做 FTS + 语义 → 融合排序
  3. 输出 TOP K 结果 + 来源引用
```

不需要启动 PostgreSQL 和 Docker，纯文件级别可跑通。

### Phase 2：数据库级检索（后续）

```text
用 Docker 启动 PostgreSQL + pgvector：
  1. 数据导入脚本（YAML → SQL INSERT）
  2. 数据库内完成 FTS + vector 检索
  3. API 封装为 FastAPI endpoint
```

## 6. 评估指标

| 指标 | 目标 | 说明 |
|------|------|------|
| Recall@5 | ≥ 0.85 | 前5个结果中包含正确法规的比例 |
| Precision@5 | ≥ 0.70 | 前5个结果中相关结果的比例 |
| MRR | ≥ 0.80 | 第一个正确结果的排名倒数均值 |
| 时效过滤准确率 | 100% | 不能返回已废止的法规 |
